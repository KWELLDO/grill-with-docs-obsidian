# 纯 Markdown 解耦说明

本分支是 `main`（Obsidian 版）的解耦版。这篇说明摘掉了什么、留下了什么，以及为什么这样切。

## 切分线：概念保全 vs 发现查询

改造 Obsidian 版时，术语结构带来两类收益：

1. **概念保全** —— 一个概念一张卡；落选的词与**排除理由**同框；索引页只索引不定义
2. **发现与查询** —— 双链反链、Bases 表、CLI 校验、改名自动改写引用

**第 1 类是纯结构收益，不依赖任何工具。** 它最有价值的产出是把「同一个词既当概念又被禁用」这类自相矛盾挤出来 —— 这只需要「一词一卡 + 互链 + 禁用词必带理由」，跟 Obsidian 无关。

**第 2 类才是 Obsidian 带来的。** 它让库更好用，但代价是：强依赖 Obsidian 1.9+、强依赖官方 CLI、产物在 GitHub 上不可点、离开 Obsidian 就退回普通文本。

所以解耦的切分线就在这两类之间：**留下第 1 类，替换第 2 类。**

## 逐项替换

| 摘掉的 | 替代 | 代价 |
|---|---|---|
| `[[双链]]` | 相对 Markdown 链接 `[订单](./order.md)` | 无 —— 相对链接在 GitHub 上可点，双链只在 Obsidian 里成立 |
| `glossary.base` / `decisions.base` | 索引页清单 + `grep` | 「哪些术语待敲定」从一条命令变成 `grep -l "status: provisional"` |
| `obsidian unresolved` | `validate.py` 检查项 1 | 无 —— 反而能同时报出行号 |
| `obsidian backlinks` | `validate.py` 检查项 5（孤儿卡） | 拿不到反链**计数**，只知道「有没有入链」 |
| `base:query` 过滤 | `validate.py` 检查项 6（待敲定一致性） | 筛选能力受限，只覆盖这一种查询 |
| `obsidian rename` 自动改写双链 | `git mv` + 跑校验 + 手工修 | **这是真实退步**，见下 |
| `aliases` frontmatter | 不设该字段，同义说法写进正文 | 打字 `[[采购单]]` 不再自动命中；靠搜索 |
| `![[glossary.base]]` 嵌入 | 索引页手写清单 | 清单要人维护，但校验脚本会核对一致性 |
| `status` 之外的展示配置 | 无 | 纯 md 没有表格视图 |

## 唯一的真实退步：改名

Obsidian 版的 `obsidian rename` 会自动改写全部指向旧名的双链，改名成本 = 1 条命令。

纯 md 没有这个能力：`git mv` 之后所有旧链接静默断掉。替代流程是三步 —— `git mv` → 跑 `validate.py` → 按报出的断链逐条修。校验脚本把「静默失败」变成了「显式报错」，这是能做的最好程度，但**成本确实比一条命令高**。

所以本分支的 `SKILL.md` 把「改名用 `git mv` 并跑校验」写成了硬规则。

## 没被摘掉的两处「Obsidian 味」

这两处保留，因为它们已经与工具无关：

- **`frontmatter`** —— 普通 YAML，`grep` 和任何静态站点生成器都能读，不是 Obsidian 专属。
- **`context` 字段** —— 多上下文分组的依据，与 `CONTEXT-MAP.md` 配套，纯 md 下同样需要。

## 验证

- `tools/selftest.sh` —— 12 项断言：基线通过 + 11 类错误逐项能被抓出
- 端到端 —— 用「反身性知识架构」那套真实产物（8 张术语卡 + 3 条 ADR + 32 个链接）跑校验，全部通过
- 本分支的 `SKILL.md` / 三个 FORMAT 文件里**不出现任何 Obsidian 命令**；`validate.py` 的残留检查会在产出物里抓 `[[`、`![[`、`.base`、obsidian 命令
