# matt SKILL 改造：结合 Obsidian，做到术语递归解释

## 0. 对比实验：改造后的 skill 到底有没有变好

### 实验设计

- **同一题目**：`知识存储与图数据库方案.md`（本库 650 行的真方案，术语模糊、决策密集）
- **同一模型、同一份「用户回答脚本」**，只换 skill 文本 → 隔离出的是 skill 文本质量，不是模型能力
- **A** = 原版 `grill-with-docs`（grilling + domain-modeling，英文规则）
- **B** = `grill-with-docs-obsidian`
- 产物：`/tmp/ab/A/` 与 `/tmp/ab/B/`（**注意：写在 `/tmp` 下，已被系统清理**。种子、复现步骤与三份关键证据已固化到发布仓的 `experiment/`，结论不受影响）

### 方法局限（先说清楚，否则结论会被读错）

1. **只跑了 1 轮**，用户回答是预先写好的脚本。**原版的核心卖点是「relentless 多轮施压」，这个实验系统性地低估了它** —— 真实多轮下它可能挖出 B 挖不出的问题。
2. 「A 少问一题」只代表我这次生成时的差异，**不能断言 A 覆盖更全**。
3. B 的产物天生在 Obsidian 库里，对比中 B 占了工具链的便宜 —— 这正是改造目的，但要说明。

### 结果

| 指标 | A 原版 | B 改造版 |
|---|---|---|
| 首轮问题数 / 带推荐答案 | 6 / 6 | 7 / 7 |
| 多问出来的那题 | — | 「**主体**」与「**来源**」是不是一回事（Q7） |
| 裁决了易混词 | 7 组 | 8 组 |
| **其中带排除理由** | **0** | **8** |
| 术语定义粒度 | 单文件 7 个词条 | 8 张独立卡 |
| 「哪些术语还没敲定」 | **答不出**（无 status 字段） | `base:query view=待敲定` 一条命令 |
| 术语 ↔ 决策的连接 | **ADR 里双链数 = 0** | `backlinks` 一次列出 4 个来源 |
| 死链检测 | 得自己写脚本 | `unresolved` 一条命令 |
| 术语改名成本 | 1 个文件 | 1 条命令（见下） |

### 三个实质性发现

**① 原版出现了自相矛盾，而 B 的结构逼出了那个区分。**

原版的词表里：

```
**Recursion**:
The return of an expanded rationality back into the system as a usable Reflection.
_Avoid_: Reflection, retrospection, update
```

定义用 `Reflection` 当一个独立概念，禁用词里又把 `Reflection` 禁掉了 —— **同一张表里既用又禁**。

B 把「回收」和「反思」拆成两张卡后，矛盾无处躲：

> **不要用来指**：反思、复盘、更新 —— 「**反思」是回收产出**的东西（见 [[reflection]]），「复盘」含有人工总结的意味，回收可以是自动的。

**这不是格式差异，是概念被保住了。** 原版允许这种矛盾存在（词表只是词表），B 的「一词一卡 + 互链 + 禁用词必带理由」把它挤了出来。

**② 禁用词带理由，原版不带。**

原版 `_Avoid_: Feedback, case, log` —— 只告诉你「别用」，不告诉你「为什么」和「那到底指什么」。下次讨论有人再说「日志」，agent 知道要质问，但**质问时说不出正确方向**。B 的每一行都是「词 + 为什么排除 + 它其实指什么 + 相关卡」。

**③ 术语改名：B 看起来更贵，实际上 1 条命令归零。**

用文件工具 `mv` 改名，模拟出 **4 处要改 + 1 个文件重命名 + 3 处残留双链**（`CONTEXT.md`、ADR、另一张卡都还指着旧 slug）。这看起来是 B 的硬伤。

但实测 `obsidian rename`：

```
$ obsidian rename file=degradation name=scope-narrowing
Renamed: glossary/degradation.md -> glossary/scope-narrowing.md
```

**所有指向它的双链被自动改写**（术语卡、ADR 全部同步），`unresolved` 回到空。改名成本 B = 1 条命令，A = 1 次编辑 —— 基本打平，而且 B 顺带得到一张实时更新的反链网络。

> **这条应该写进 skill**：术语改名必须用 `obsidian rename`，用文件工具 `mv` 会静默留下断链。这正好补上了我之前没验证的空白。

### 结论

改造版在**可查询性、可连通性、概念精度**三项上明显更强，且第 ① 条是真实的质量提升而非包装。改造版的代价是**结构复杂度**（8 个文件 vs 1 个）和**对 Obsidian 的强依赖**（改名、反链、Base 全部依赖官方 CLI 或 Obsidian 本体）。

**但这个实验不足以判定「改造版全面优于原版」** —— 多轮施压这一项被脚本化答案掩盖了，而那正是原版最强的地方。诚实结论是：**在概念无损与知识库可用性上，改造版赢了；在交互压力上，本实验没有测到。**

## 关键约束：Base 是文件级的

Base 的**一行 = 一个文件**，属性挂在文件 frontmatter 上。所以「术语表做成一张 Base」这个需求，直接否掉了原版「单文件 `CONTEXT.md` 紧凑术语表」的做法。

两条路：
- **A（选了）** 术语拆成 `glossary/<slug>.md` 一词一卡，`CONTEXT.md` 降级为索引页
- **B** 保住单文件术语表，双链只在 ADR ↔ CONTEXT 之间做，Base 放弃

## 定下来的决策

1. **新建变体，不改原版** —— `grilling` / `domain-modeling` / `grill-with-docs` 一个字没动
2. **选 A**：术语独立成卡，双链和 Base 才真正能工作
3. **中文化范围**：正文全中文，但 `CONTEXT.md`、`docs/adr/`、`.base` 键名等**标识符保持英文**（Obsidian Bases 的 schema 固定）
4. **目录/文件名用英文，术语内容用中文**：`glossary/order.md` 里 `term: 订单` —— 双链 `[[order]]` 稳定、跨语言可读、Base 排序不炸
5. **两张 Base**：`glossary.base`（术语总表）+ `decisions.base`（决策总表），懒创建
6. **索引页只索引不定义** —— `glossary/order.md` 是 single source of truth，改词只改一处
7. **不加实现细节进术语卡** —— 它是术语表，不是规格书

## 关于禁用词：一次讨论，三层认识

源头规则（`domain-modeling`）：**必须有主张** —— 同一概念多个词时挑一个作规范词，落选的写进 `_Avoid_`。它解决的是**同义词漂移**：不裁决的术语表会退化成同义词词典。

这轮讨论把它翻了三层：

**一、原来的「唯一真源」被我劈裂了。** 原版 `_Avoid_:` 是行内斜体，词和理由在定义正下方，天然一体。我却同时写进 frontmatter `avoid:` 数组**和**正文「不要用来指」—— 两处可编辑必然漂移。而且 Base 表格里那格只有「交易」两个字，看不出为什么错、错到哪去：**质问的那一刻恰好缺了最需要的那个信息**。

**二、`aliases` 和被禁词语义相反，我差点把它们当同一类。**
- `aliases` = 照认（这些词命中这张卡）
- 被禁词 = 说错了

绝不能交叉：把「交易」写进 `aliases`，Obsidian 会让 `[[交易]]` 真的打开 `order.md` —— **等于把禁令注册成快捷方式，语义整个反转**。这是 `aliases` 唯一成立的理由：它是 Obsidian 原生属性、有真实机械效果，所以是真增强；而禁用词没有任何原生对应物，只配留在正文。

**三、中文让这条规则更重，不是更轻。** 英文里同一概念的候选词往往同源（order / purchase），中文里一个 `customer` 能落到客户/用户/顾客/买家/甲方五六个落点，还叠上音译借词与行业黑话。不裁决的代价中文远高于英文。

**结论**：`glossary.base` 不设禁用词列 —— 查「这个词是不是被禁」是**读这张卡**的动作，不是**扫全表**的动作。禁用词只写在正文一行：词 + 为什么排除 + 它其实指什么 + 相关卡。

## 校验脚本抓出的第二个缺陷：`slug` 是冗余字段

写了脚本交叉校验三份文件的「模板 frontmatter 键 == 字段表键 == Base 声明属性」，发现 `glossary.base` 少声明 `slug`。追下去发现 **`slug` 根本不该存在**：它就是文件名去掉 `.md`。存两遍早晚漂移 —— 文件叫 `order.md` 而 frontmatter 写着 `purchase`，双链就废了。

**删除该字段**，并写明理由防止以后被加回来。改名时文件名要跟着改（文件名就是双链目标）。

## 复核时发现并修掉的 4 个问题

对着原版逐条比对（`grilling` 9/9 机制、`domain-modeling` 14/14 要素全部保留），发现 4 处：

1. **英文残留**：description 里 `relentless 地拷问` → `不依不饶地追问`
2. **开工前漏读 ADR**：只让读 `CONTEXT.md` 和 `glossary/`，会重复讨论已记录的决策。改成**按 Base 读全**（读 `.base` 拿字段定义 → 读背后笔记取内容），并把库里其他笔记（日记、会议记录）也纳入捞取范围
3. **`CONTEXT-MAP.md` 模板抄了一份 → 造成分叉**。改回指针：`domain-modeling/CONTEXT-FORMAT.md` 才是唯一真源（那份格式我本地已装，指针落得到实处）。只留四条 Obsidian 专属补充：全仓挂表入口、编号全仓统一、术语卡只放一处、各上下文 `CONTEXT.md` 是窄索引页
4. **ADR 的 `status` 从必填改回可选** —— 落盘意味着决策已和用户敲定过，缺省即 accepted；只在 `proposed`/`deprecated`/`superseded` 时写。术语卡的 `status` 保持必填（`settled`/`provisional`），因为「哪些词还悬」是这张 Base 存在的意义

## 校验：写了脚本，不靠眼睛

交叉校验这些不变式（YAML 可解析、三份文件字段一致、Base 声明属性 == 字段表键 ∪ `file.name`、视图 `order` 不引用未声明属性、无重复键）：

- **必填字段必在模板** —— 声明必填却没在模板里出现 = 假的必填
- **可选字段允许不在模板** —— ADR 的 `status` 就是这种（字段表说明它存在，模板默认不写）
- **视图里不引用未声明属性** —— 抓出过一次重复 `order:`/`filters:` 键

另外查了：`./` 引用无死链、中文文件无英文句子残留、四个 harness 软链到位、原版三个 skill 时间戳未变。

## 原则沉淀

> **行为**在我这份（中文 + 拷问纪律 + 当场落盘）；**与 Obsidian 无关的格式**在 `domain-modeling`（唯一真源）；**Obsidian 侧产物**在我这份。

抄一份别人的格式规则 = 造一个会过期的分叉。只增强属于自己领域的那部分。

推论：**一个字段只有在有原生机制支撑时才搬进 frontmatter**（`aliases` 有），否则留在正文（禁用词）。搬进去的收益要能说清楚，说不清就是重复。

## 重大发现：官方 Obsidian CLI + 三个官方 skill

本来打算手写一份 CLI 命令表，查了一下才发现**官方 CLI 已经装好了**：`~/.local/bin/obsidian`（Obsidian 1.9+ 内置，走 `$XDG_RUNTIME_DIR/.obsidian-cli.sock`，需 Obsidian 运行中）。它有两条命令是文件系统视角根本拿不到的：

- **`base:query`** —— 真的按 Base 过滤+渲染，直接返回表格
- **`unresolved`** —— 权威的全库死链清单

所以本 skill 的「按 Base 读」从「手写正则模拟」升级成了真命令。

### 装了三个官方 skill（`kepano/obsidian-skills`，kepano 是 Obsidian CEO）

| skill | 行数 | 作用 |
|---|---|---|
| `obsidian-cli` | 106 | CLI 全部命令、`file` vs `path` 的区别 |
| `obsidian-bases` | 499 | `.base` 完整 schema、filter 语法、函数 |
| `obsidian-markdown` | 196 | 双链、嵌入、frontmatter 属性语法 |

**而且它们反过来抓出了我手写模板的三个真 bug：**

**① `id: 0001` 被 YAML 解析成数字 `1`** —— 前导零被吃掉，Base 里渲染成 `1`/`2`，编号错位。改用 `formula.adr_no: 'file.name.split("-")[0]'` 从文件名派生。跟术语卡不存 `slug` 是同一条道理：**同一信息不存两遍**。

**② `sort` 不在官方 schema 里，实测也无效** —— 而**零填充文件名天然就是有序的**（`0001 < 0002`），这个键从来就是多余的。

**③ Obsidian 对未知键静默忽略** —— 我故意写 `bogusKey: 1` 进去，表照样正常渲染。**「能报错」不能证明 `.base` 写对了**，必须对着 schema 逐个核键名。这条写进了收尾清单。

### 读/验证走 CLI，写走文件工具

不是偏好，是能力差异：CLI 强在图谱视角（`base:query` 真渲染、`unresolved` 权威）；而 `create content=` 传多行 YAML 要转义换行和缩进，极易被 shell 吃掉。建卡、改 frontmatter 改名用文件工具。

### 五个实测坑（都写进 SKILL.md）

1. `base:views` **不接受 `path`**，只看活动文件 → 直接用 `base:query view=<名字>`
2. `format=md` 表头用**原始属性名**，不套自定义 `displayName`（`formula.*` 列除外）→ 核数据用属性名
3. 第一列值是**不带扩展名的文件名**（`order` 不是 `order.md`）
4. 新写完文件 Obsidian 可能还没索引完 → 先 `reload` 再查
5. **`reload` 之后 vault 短暂不可用**，任何命令报 `Vault not found` → 等两三秒

（我自己的校验脚本也踩了同一个坑：`.base` 文件的 `Path.stem` 取到 `glossary` 而非 `glossary.base`，跑出两个假死链。）

## 冒烟测试：造了个假 vault 跑一遍

文档内部一致 ≠ 产物能用。所以照模板生成了一个假 vault（3 张术语卡 + 2 条 ADR + 索引页 + 两个 base），查五件事：

| 检查 | 结果 |
|---|---|
| Base 声明的属性 vs 真实 frontmatter | 全覆盖 ✓ |
| 筛选器能否命中真实取值 | `status == "provisional"` 命中 ✓；ADR 的「未定」视图命中 ✓ |
| 14 条双链能否解析 | 0 死链（`obsidian unresolved` 确认）✓ |
| 索引页清单 vs 实际文件 | 无遗漏 ✓ |
| `related`/`terms` 是否只指向存在的卡 | ✓ |
| `.base` 骨架键是否全在官方 schema 内 | ✓ 无 `sort` |
| 每个声明的属性是否至少有一个视图展示 | ✓ 无死配置 |
| 每个视图是否含 `file.name` 列（点得回原文） | ✓ |

**又拓到两个真问题**：
- `glossary.base` 声明了 `related` 却无任何视图展示它 —— 死配置，补进卡片视图
- `decisions.base` 的「未定与已废弃」视图**没有 `file.name` 列** → 表格里点不回 ADR 原文，补上
